# ByteTrace 下一大版本方案

> 日期：2026-09-08  
> 分析基线：当前源码 v0.1.29  
> 状态：**已归档**（2026-09-30 被 [ROADMAP.md](ROADMAP.md) 取代，不再维护）  
> 原文状态：规划文档，尚未实施；新增表、模块名和验收目标均为建议  
> 开发与分发约束：不依赖 Apple 付费开发者身份，不增加 root 权限，不启用 Network Extension

## 1. 目标与范围

下一大版本围绕“历史可查、数据可信、长期运行稳定”展开。保留双通道 nettop 和 SQLite，升级查询能力、采集状态记录与后台执行架构。

| 目标 | 具体使用场景 |
| --- | --- |
| 查询历史 | 查看某一天、上个月或自定义日期范围内的应用流量 |
| 解释变化 | 找出本周比上周多用了多少，哪些应用贡献最大 |
| 判断数据是否完整 | 知道没有流量记录是正常空闲、暂停采集还是通道异常 |
| 长期保存数据 | 长期运行时界面保持响应，支持备份、恢复和结构化导出 |

| 必须交付 | 后续增强 | 暂不纳入 |
| --- | --- | --- |
| 自定义日期范围、历史切换 | 最近带宽、活跃应用排行 | 系统级断网、限速 |
| 周期对比、应用增量排行 | 用量阈值提醒 | 全量连接、域名历史 |
| 双通道运行状态与历史缺口 | 自定义分组和别名 | 云同步、多设备合并 |
| 后台存储与查询、可靠退出 | 长期小时汇总 | 替换 SQLite、恢复 NetworkExtensionLab |
| 完整备份恢复、CSV 导出 | 更复杂的异常检测 | 默认有损采集模式 |

首版不必同时完成全部增强项。“最近带宽”和“异常提醒”需要新的时间窗口语义，不宜在存储重构过程中一起引入。

## 2. 历史查询与周期对比

### 2.1 日期范围

当前只有最近 10 分钟、最近 1 小时、今天、本周、本月五个范围，但数据库已经保留更多日汇总。首先让现有数据能够被完整访问。

在现有时间选择器中增加：

- 昨天、上周、上月。
- 指定某一天。
- 自定义起止日期。
- 上一周期、下一周期切换。

第一版自定义范围建议采用日期级选择，不支持任意秒或任意分钟。已有分钟桶无法精确切分桶内流量，日期级选择更容易保持结果含义清晰。

| 查询范围 | 汇总来源 | 趋势来源 |
| --- | --- | --- |
| 最近 10 分钟、最近 1 小时 | 分钟桶 | 分钟桶 |
| 今天、指定历史日期 | 日汇总 | 可用的分钟桶 |
| 跨日范围 | 日汇总 | 日汇总 |
| 历史分钟数据已清理 | 日汇总继续展示 | 明确提示明细不可用 |

内部时间区间统一使用“包含开始、不包含结束”，避免相邻范围在边界重复计算。日汇总继续按既定本地日期读取，不能直接用 UTC 日期替代。

### 2.2 周期对比

| 对比方式 | 示例 | 使用条件 |
| --- | --- | --- |
| 完整周期对比 | 上周与上上周、昨天与前天 | 两个周期均已结束 |
| 同进度对比 | 今天截至 15:00 与昨天截至 15:00 | 对照区间具有足够明细 |

分钟桶已删除时，不能从整日总量推算上午或下午的用量。此时禁用同进度对比，保留整日比较。分钟粒度边界也应明确，不承诺桶内任意时刻的精确切分。

应用排行增加三个排序入口：本期总量、增加最多、减少最多。展示本期、对照期、字节差值和变化率。对照期为零时显示“新增流量”，不展示无穷大百分比。

### 2.3 验收

- 跨月、跨年、周起始日和夏令时日期的范围正确。
- 只有日汇总或部分明细缺失时，仍展示有依据的结果。
- 快速切换日期时，不被旧查询结果覆盖。
- 代理运输流量继续单独展示，不计入应用总量和应用总量变化。

## 3. 采集完整性与数据解释

### 3.1 状态模型

缺少流量点不能直接说明停止采集；应用正常空闲也可能没有记录。需要把流量数据和采集运行情况分别保存，再共同用于解释图表。

外部通道、补充通道分别记录：

| 状态 | 含义 |
| --- | --- |
| 启动中／建立基线 | 尚不能提供正常增量统计 |
| 正常运行 | 持续收到符合格式的采样帧 |
| 等待重连 | 子进程退出或网络变化后正在恢复 |
| 格式不兼容 | 当前系统输出无法按既定格式读取 |
| 已暂停／休眠 | 当前没有执行采集 |
| 状态未知 | 无法确认这一段时间是否正常运行 |

界面分两层：

- 菜单面板展示当前状态，例如“统计中”“补充采集不可用”“正在恢复”。
- 主窗口在历史趋势中标出暂停和异常区间，点击可查看原因与持续时间；明细已清理与未采集分开解释。

不能把“正常运行 99% 的时间”写成“流量准确率 99%”。正常采样仍存在短连接、启动基线等观测限制；两条通道也不能简单取平均，生成容易误解的总分。

### 3.2 健康检查与持久化

在既有定时任务中检查最后有效帧时间，超出阈值后先标记异常，再按已确认的规则决定是否重启。阈值按两个通道分别设置，并为调度延迟留余量，避免过度重启造成更多基线缺口。

存储采用状态变化记录和低频检查点，不为每个 1 秒采样帧新增永久数据库记录。异常退出后，最后检查点之后的区间标为未知，不推断应用一直正常运行。

旧历史缺少这些记录时，显示“未记录采集状态”，不能回填成正常。

### 3.3 验收

覆盖零流量但帧正常、仅补充通道异常、用户暂停、睡眠唤醒、进程异常退出、重启恢复及旧版本历史数据。检查健康阈值不会在正常调度延迟下频繁触发重启。

## 4. 后台执行架构

### 4.1 职责拆分

当前归属、写入、查询和 UI 编排集中在 `ByteTraceViewModel`，其中多个操作同步运行在主线程。建议逐步形成以下职责边界：

| 建议模块 | 负责内容 |
| --- | --- |
| `CollectionCoordinator` | 双通道启动、停止、重连、运行代次和健康状态 |
| `UsagePipeline` | 帧时间恢复、过滤、进程归属、聚合 |
| `UsageRepository` | 写入、查询、清理、备份与迁移 |
| 界面模型 | 查询参数、加载状态、结果发布 |

这些首先是职责边界，不要求机械地拆成四个大型对象，也不要求全部改成 actor。采用 actor 本身不代表更快或更省电。

执行顺序：

```text
采集帧 → 有序处理 → 聚合 → 串行提交 → 发布数据版本 → 按需查询 → 更新界面
```

### 4.2 关键并发约束

**采集事件带运行代次。** 每次启动或重启生成新的代次标识，避免旧进程延迟回调修改新一轮采集状态。停止时，旧代次尾帧仍需被正确排空，不能一律丢弃。

**归属保留必要的主线程边界。** 可以后台执行的系统调用、过滤和合并移到后台；依赖 AppKit 的元数据读取单独处理。不能整段搬到后台后，再通过同步等待主线程造成死锁。

**先采用单一串行存储执行器。** 写入、清理和查询从主线程移出，初期继续沿用现有连接和事务保护。只有历史查询确实阻塞写入时，再增加独立读连接，避免一次性改变太多并发条件。

**异步查询只发布最新请求。** 查询条件包含日期、应用、显示过滤和请求版本。切换条件后，旧结果即使完成也不再发布。一个页面的总量、排行、趋势应来自同一份一致结果。

**异步写入保持批次所有权。** 明确待写、写入中、失败重试的状态。现有 UPSERT 是累加写入，不得复制 pending 后提前清空或让同一批次被重复提交。

**退出使用完成确认。** 替换当前依赖短时间 RunLoop 排空的做法：停止接收新帧、结束子进程、排空尾帧、完成最后事务，再允许正常退出。用户强制结束进程仍可能损失未提交数据，普通退出流程不能消除这一限制。

### 4.3 验收

- 写入失败后重试不双计。
- 停止时尾帧不丢失。
- 快速暂停恢复不会混用运行状态。
- 清空数据不会被旧队列重新写回。
- 退出期间没有死锁或遗留子进程。
- 保留清理与写入之间不存在事务交错。

## 5. 数据库升级

### 5.1 增量迁移

继续使用 SQLite，采用累加迁移。首版只增加支撑实际功能的数据，不重写现有历史表。

| 数据 | 建议用途 | 首版是否需要 |
| --- | --- | --- |
| 采集会话 | 记录启动、正常退出、采集口径及时间环境 | 是 |
| 通道状态区间 | 保存状态开始结束、原因和最后确认时间 | 是 |
| 数据维护元信息 | 记录明细清理范围、备份格式等 | 按展示需要增加 |
| 小时汇总 | 分钟清理后保留长期日内趋势 | 否 |
| 分组与别名 | 用户自定义展示，不改变原始身份 | 否 |

采集会话属于首版必需数据。具体表名、字段和索引在实施前结合查询设计确定。

数据库结构版本与统计口径版本继续分离。新增采集状态表不改变旧流量含义，不应让已有历史突然不可见。改变字节归属或时间口径时，则单独设计兼容策略。

### 5.2 时间语义

当前采样时钟拼接处理当天日期，跨午夜可能归错日期。建议在接收帧时保存完整接收时间，结合前一帧顺序恢复采样日期；速率和超时计算采用单调时间，展示与日期归属采用日历时间。

历史日汇总无法无损转换成任意时区的新日汇总。建议先保留“采集时本地日期”的历史语义；跨时区展示明确提示，不在迁移时重新分摊历史流量。具体规则在实现时间模块前确认。

### 5.3 查询与容量

用真实历史规模和查询计划评估索引，尤其是单应用时间范围查询，不凭表面字段组合直接增加索引。

读写分离作为第二步。WAL 可以支持跨连接读写并发，但仍只有一个并发写入者。若引入独立读连接，必须限制长读事务，防止长期占用快照导致 WAL 持续增长。参见 [SQLite WAL 文档](https://www.sqlite.org/wal.html)。

小时汇总后续若实施，应从仍存在的分钟桶生成，并使生成过程可重复执行而不重复累计。已经清理的分钟历史无法从日汇总还原成小时数据。

## 6. 备份、恢复与导出

当前范围 JSON 导出继续保留，新增两种明确不同的能力：

| 功能 | 内容 |
| --- | --- |
| CSV 导出 | 当前筛选范围的应用统计，便于表格分析 |
| 完整备份 | 全部数据库历史及必要版本信息，用于恢复 |

完整备份使用 SQLite Backup API 生成一致快照，不能只复制运行中的主数据库文件。参见 [SQLite Backup API](https://www.sqlite.org/backup.html)。

恢复流程：

1. 检查文件、完整性和版本兼容性。
2. 展示备份时间与数据范围。
3. 用户确认覆盖。
4. 暂停采集并排空。
5. 自动备份当前数据。
6. 替换并校验，失败时恢复原数据。
7. 恢复采集。

第一版仅支持替换恢复。备份合并涉及同一时间段重复数据识别，当前累计模型没有可靠的跨备份去重依据，不应简单相加。

CSV 明确包含统计范围、上下行字节、应用身份和分类。应用名称等文本需正确转义，并处理表格公式前缀，不能只拼接逗号。

验收覆盖采集中备份、损坏文件、较新版本备份、磁盘空间不足、恢复中断，以及覆盖前自动备份是否可用。

## 7. 性能与功耗优化

### 7.1 目标

| 类别 | 应达到的结果 |
| --- | --- |
| 交互性能 | 主线程不再同步等待 SQLite 事务和大范围查询 |
| 后台功耗 | 在相同流量与设备条件下，整套进程的资源消耗不回退 |

优先实施：

- 无数据变化时减少重复查询，但保留滚动窗口过期、跨日及状态变化更新。
- 对历史范围缓存结果，新增流量只使受影响的范围失效。
- 确认同帧重复进程解析是否存在，避免重复系统调用。
- 控制队列积压和缓存大小，数据库错误时不能无限增长。
- 保留当前 5 秒落库目标，不通过延长持久化间隔制造省电收益。

已有 `-c`、身份缓存、零字节预筛、SQL 批处理、图表缓存和分批清理继续保留。默认不降低补充采样频率，也不因系统代理关闭就停掉补充通道。

### 7.2 验证方法

| 验证 | 标准 |
| --- | --- |
| 固定 CSV 回放 | 每应用、每方向、每时间桶结果一致；时间修复的预期差异单独说明 |
| 真机对照 | 统计 ByteTrace 与两个 nettop 的总 CPU、唤醒、内存、磁盘写入和交互延迟 |

场景至少包括空闲、持续下载、短连接密集、系统代理、TUN、历史大范围查询和保留清理。功耗改善幅度在测量后确定，不预先承诺百分比。

解析器进一步优化只在热点证据明确后进行。字节级扫描、字符串分配优化需要固定 CSV 回放验证，不能仅凭代码变短或分配次数猜测准确性和实际收益。

## 8. 后续增强方向

### 8.1 最近带宽与活跃应用

复用现有采集结果，在内存维护短时窗口，展示最近窗口平均上下行速率及活跃应用排行。外部通道每 5 秒采样，不能包装成精确的 1 秒瞬时速度，也不需要把秒级记录长期写入 SQLite。

两个通道需采用可解释的统一窗口，并处理启动基线、重连及数据延迟。展示窗口长度，让速率含义明确。

### 8.2 用量提醒

先支持每日应用用量阈值，再考虑持续大量上传。后者需要冷却时间、最小持续时长和采集缺口处理。本地通知需用户授权，并在正式 ad-hoc 安装包上验证表现；不引入远程推送服务。

### 8.3 分组、别名与小时汇总

分组与别名单独保存，不修改原始 `appKey`，避免切断历史连续性。小时汇总只在长期日内趋势需求确定后引入，避免首版增加多份统计维护成本。

## 9. Apple 开发者身份边界

首版方案不依赖 Network Extension，也不要求新增特权组件。

发布继续采用当前 ad-hoc 路径，首次安装的 Gatekeeper 放行问题仍然存在。功能升级不能解决签名身份限制。Developer ID 与公证需要相应开发者资格，ad-hoc 签名不能用于公证。

- [Apple Developer ID](https://developer.apple.com/developer-id/)
- [公证要求](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)
- [Network Extension 配置](https://developer.apple.com/documentation/xcode/configuring-network-extensions/)

自动更新若要做，应另立分发方案，不放进本次数据与架构升级范围。`NetworkExtensionLab/` 继续保持冻结。

## 10. 实施顺序与发布门槛

| 阶段 | 交付内容 | 进入下一阶段的条件 |
| --- | --- | --- |
| 第一阶段：口径确定 | 日期范围、时间归属、采集状态、恢复规则 | 关键语义无歧义 |
| 第二阶段：后台管线 | 有序采集、后台存储、可靠停止退出 | 回放等价，失败重试与尾帧验证通过 |
| 第三阶段：状态存储 | 新表迁移、状态区间、异常恢复 | 旧历史保留，异常区间不误标正常 |
| 第四阶段：用户功能 | 历史查询、对比、完整性展示 | 各时间与缺失数据场景正确 |
| 第五阶段：数据管理 | CSV、完整备份与替换恢复 | 恢复失败可保留或恢复原数据 |
| 第六阶段：发布验证 | 性能对照、长时间运行、安装升级 | 无统计回退、无子进程残留、迁移可恢复 |

不要一次性合并所有改动后再验证。每个阶段保留可复核结果和独立提交，让采集变化、数据迁移与界面变化能够分别检查。

发布前至少要求：

- 现有测试通过。
- 新增时间、迁移、队列和恢复测试通过。
- 双通道真实场景验证通过。
- 完成一次覆盖休眠唤醒与网络切换的长时间运行。
- 真实旧版本数据库升级后历史可读，恢复路径可用。

具体执行时再说明测试范围和耗时。本方案保存不代表已执行上述验证，也不构成修改代码、提交或发布的授权。

## 11. 实施前待确认的产品决策

建议采用以下默认方向，但尚未作为已确认需求：

1. 自定义范围先采用日期粒度。
2. 历史按采集时本地日期保留，跨时区不重算旧日汇总。
3. 首版恢复只做覆盖恢复。

首版四项核心交付为：历史日期与周期对比、双通道采集完整性、后台存储与可靠退出、备份恢复。
