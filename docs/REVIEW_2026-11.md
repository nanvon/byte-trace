# ByteTrace 方案评审记录（2026-11-11）

> 代码基线：`8ae3281`（v0.1.41 之后），本机 macOS 27.2.1（26B131）
> 前提：不使用 Apple 付费开发者身份，不加 root，不启用 Network Extension，ad-hoc 签名
> 状态：评审结论与待办，均未实施。每一条标注了「已实测」或「未验证」，实施前应逐条复核。交付时从 §8.7 的任务清单开始读。

## 结论

值得更换的只有数据源一处：从「启动 nettop 子进程解析 CSV」改为直接调用 nettop 使用的系统私有框架 `NetworkStatistics.framework`（下称 NStat）。其余设计（宿主 + 程序两级归属、分钟桶 + 日汇总、代理流量单独记录不抵扣）评审后认为合理，不建议改动。存储另有一个体积问题，与数据源无关，可以先修。

## 1. 数据源改为 NStat

### 1.1 已实测的事实

- `/usr/bin/nettop` 带 entitlement `com.apple.private.network.statistics`，但本机 `sysctl net.statistics_privcheck` 为 `0`，内核不检查该权限。
- 未签名、无 root、无 entitlement 的普通进程 `dlopen` `/System/Library/PrivateFrameworks/NetworkStatistics.framework/NetworkStatistics` 后，可以拿到全系统 TCP/UDP 连接：运行 14 秒收到 469 条连接新增、161 条移除。
- 已关闭连接有最终计数：`curl --noproxy '*'` 下载 5,000,000 字节，连接移除时最后一次计数为 rx 5,012,448 / tx 543（100.2%，多出部分是 TLS 开销）。探针每 5 秒才主动查询一次，连接在两次查询之间关闭，最终值仍然完整。
- 每条连接的描述字典包含：`processID`、`uniqueProcessID`、`processName`（不截断）、`epid`、`eupid`、`euuid`、`localAddress` / `remoteAddress`（sockaddr 的 `Data`）、`interface`（接口索引）、`ifLoopback` / `ifWiFi` 等接口类型标记、`startAbsoluteTime`、`rxBytes` / `txBytes`、`rxWiFiBytes` / `rxWiredBytes` / `rxCellularBytes` 及对应 tx 分项、`TCPState`、`provider`（TCP / UDP）。
- 代理内核（mihomo）自身连接的 `epid` 等于自己的 pid，与 CLAUDE.md 中「nsurlsessiond 无法按 epid 拆分」的结论一致，NStat 不能解决这一点。

### 1.2 可以删除或简化的现有机制

| 现有机制 | 位置 | 换后 |
| --- | --- | --- |
| 两个常驻 nettop 子进程，补充通道 1 秒采样 | `NettopCollector` | 进程内回调，无子进程 |
| CSV 解析、零字节预筛、端点字符串解析 | `NettopCSVParser`、`CSVLineParser` | 直接读字典与 sockaddr |
| 已关闭连接残差按 30 秒历史推断 | `SupplementalResidualTracker` | 不需要，连接移除时有最终值 |
| 外部通道重启间隙补偿、首帧基线丢弃 | `NettopRestartGapRecovery` | 连接计数是累计值，重连后按连接做差 |
| 时钟嫁接日期、跨零点回退 | `NettopSampleClock` | 用接收时的本机时间 |
| `NSUnbufferedIO`、空 stdin Pipe、POSIX `read()`、`-c` | `NettopCollector` | 不需要 |
| 进程名最多 15 字符、按名称回填归属 | `process_names` 表、`ProcessAttributionCache` 名称映射 | 进程名完整；进程已退出时仍可能需要回填，需确认 |
| pid 复用靠 `(pid, processStartTime)` | `ProcessAttributionCache` | 可改用 `uniqueProcessID`，需确认它在进程退出后是否仍可用于查身份 |

直连 / 代理的判断从「按通道推断」变为「逐连接判断」：接口为 utun 且有明确端点，或远端等于系统代理回环端点，记 `proxied`；其余非回环接口记 `direct`。mihomo 连接表匹配继续用应用侧本地端点。

### 1.3 未验证，实施前必须确认

1. CPU 与唤醒数：没有测。需要与现状（外部 5 秒 + 补充 1 秒）做同条件 A/B。
2. QUIC 与用户态协议栈连接（Network.framework）是否被 `NStatManagerAddAllTCP` / `AddAllUDP` 覆盖，口径是否与 nettop 一致。
3. 与 nettop 的数据等价：并行运行，按进程、按方向逐项对账。沿用 `--accuracy` / `--routes` / `--restart-check` 的用例。
4. 睡眠唤醒、网络切换、长时间运行（数天）下回调是否中断、是否需要重建 manager。
5. 连接数很多时（上千条）回调与查询的开销；是否可用 `NStatManagerAddAllTCPWithFilter` / `WithOptions` 在内核侧过滤回环噪声。这几个函数的参数含义未确认。
6. `NStatManagerSetFlags`、`NStatSourceSetEventsBlock`、`NStatManagerQueryAllSourcesUpdate` 的用途未确认。
7. 连接移除回调到达时进程可能已退出，身份解析（`proc_pidpath` 等）会失败。需要在连接新增时就解析并缓存归属。
8. 外部通道目前用 `-P` 进程行，天然包含所有外部接口；NStat 是逐连接的，需要确认按连接累加后与 `-P` 进程行总量一致。

### 1.4 风险

- 私有框架，没有兼容性保证。系统升级可能改函数签名、字典键或打开 `privcheck`。
- 因此 nettop 管线必须保留为回退：启动时探测 NStat 是否可用（`dlopen` 成功、manager 创建成功、若干秒内收到回调），不可用时走现有双通道。
- 两套数据源不能同时写库，切换时要防止重复计数（写入是累加的）。
- 是否需要新的 `accounting_version`：口径上 NStat 更完整（短连接不漏），与现口径 3 的数字会有系统性差异。未决定，倾向于不升版本，因为含义相同只是更准。

### 1.5 建议的实施步骤

1. 在 `ByteTraceProbe` 增加 NStat 模式，只读、不落库，与 nettop 并行输出对账结果。
2. 完成 1.3 的各项验证，记录数字。
3. 在 `ByteTraceCore` 增加 NStat 采集器，输出与现有管线相同的中间结构（进程 + 上下行字节 + 路径），聚合与存储不改。
4. 正式管线增加数据源选择与自动回退，默认仍用 nettop，设置里加开关试运行一段时间。
5. 稳定后把 NStat 设为默认，nettop 保留为回退。

### 6.1 NStat 接口语义（对应 1.3 第 2、5、6 项）

C 函数都是对 ObjC 类 `NWStatisticsManager` 的薄封装（反汇编）：

| C 函数 | 实际签名 | 转发到 |
| --- | --- | --- |
| `NStatManagerAddAllTCPWithFilter` | `(mgr, uint64_t filter)` | `addAllTCP:events:pid:uuid:`，后三个参数为 0 |
| `NStatManagerAddAllTCPWithOptions` | `(mgr, uint64_t filter, uint64_t events, int32_t pid, void *uuid)` | 同上 |
| `NStatManagerAddAllUDPWithFilter` / `WithOptions` | 同 TCP | `addAllUDP:events:pid:uuid:` |
| `NStatManagerQueryAllSources` | `(mgr, block)` | `queryAllCounts:`，发内核消息 1004（`QUERY_SRC`，只有计数） |
| `NStatManagerQueryAllSourcesDescriptions` | `(mgr, block)` | `queryAllDescriptions:`，消息 1005（`GET_SRC_DESC`） |
| `NStatManagerQueryAllSourcesUpdate` | `(mgr, block)` | `queryAll:`，消息 1007（`GET_UPDATE`，计数与描述合并在一条消息里） |
| `NStatManagerSetFlags` | `(mgr, x1)` | 推断为 `setMgrflags:`，含义没读，不要调用 |

`uuid` 参数的类型（`uuid_t *` 还是 `NSUUID *`）没确认，一律传 `NULL`。Query 三个函数与 selector 的对应关系是按跳转桩地址顺序推出的（推断），探针里各调一次、看回调字典内容即可确认。

`filter` 的第 24–30 位由框架自己解释，发给内核前会清掉（反汇编 `addAllTCP:events:pid:uuid:` 与 `addAllUDP:…`）：

| 位 | 含义 |
| --- | --- |
| 28（`0x10000000`） | 订阅内核协议栈：TCP 为 provider 2，UDP 为 provider 4 |
| 29（`0x20000000`） | 订阅用户态协议栈：TCP 为 provider 3，UDP 为 provider 5 |
| 30（`0x40000000`，仅 UDP） | 订阅 provider 8（用户态 QUIC） |
| 24、25 | 配合 `pid` 使用，`pid == 0` 时被清掉 |
| 26、27 | 配合 `uuid` 使用，`uuid == NULL` 时被清掉 |

第 28–30 位一个都没置位时等同全部置位。所以探针现在用的 `NStatManagerAddAllTCP` / `AddAllUDP`（filter 为 0）已经订阅了内核 TCP/UDP、用户态 TCP/UDP 和用户态 QUIC，1.3 第 2 项在订阅层面成立；运行时是否真有 provider 3/5/8 的来源带字节回来，仍要实测（见 6.5）。provider 编号与名称的对应（2 = `TCP_KERNEL`、3 = `TCP_USERLAND`、4 = `UDP_KERNEL`、5 = `UDP_USERLAND`、8 = `QUIC_USERLAND`）来自对 xnu 的记忆，请对照头文件。

这里有一个容易踩的冲突：内核头文件里 `0x10000000` 是 `NSTAT_FILTER_SUPPRESS_BORING_CLOSE`（关闭时不发最终计数），`0x20000000` 是 `SUPPRESS_BORING_POLL`。经框架函数传入时这两位被当作 provider 选择位并清掉，不会传到内核，所以「连接移除时有最终计数」不会被 filter 关掉。不要绕过框架直接写内核控制套接字。

其余低位推断为原样传给内核（`addAllForProvider:filter:events:pid:uuid:` 没读）。xnu 头文件里可能有用的两项：`NSTAT_FILTER_ACCEPT_*`（`0x1` 起，按接口类型筛选）和 `NSTAT_FILTER_PROVIDER_NOZEROBYTES`（`0x400000`，不上报零字节来源）。用法：先用 filter 0 做完全部对账，再在探针里单独试 `0x400000`，对比来源数量、CPU 和字节合计；字节合计不完全一致就不用。正式采集器的第一版固定用 filter 0。

`NStatSourceSetEventsBlock` 对应内核的 `NSTAT_EVENT_SRC_*` 事件，需要在 `WithOptions` 的 `events` 里订阅才会有回调。本项目用不到，不要接。

`NStatManagerCreate` 回调的第二个参数仍未确认，不要读它。

对 1.1 的一处修正：进程名「不截断」没有依据。内核描述符里 `pname` 是 64 字节（xnu 头文件），实际长度取决于内核填入的进程名，可能仍有上限（推断为 32 字节）。探针里用一个长名称进程确认；归属一律以 pid / `uniqueProcessID` 为准，进程名只作展示兜底。

### 6.2 NStat 采集器的计数规则（对应 1.5 第 3 步）

每个来源（一条连接）在采集队列上维护一份状态：上次的 rx / tx、归属快照（pid、`uniqueProcessID`、进程名）、是否已有基线。规则：

1. **启动基线**。计数是连接生命周期累计值。采集器启动时已存在的连接，第一次收到的计数只记为基线，不产出流量，否则每次启动都会把这些连接的历史字节重记一遍。判定「启动时已存在」：manager 创建后立即发一次全量查询，在这次查询的完成回调之前首次出现的来源都算已存在。`startAbsoluteTime` 可以用来把这个窗口内新建的连接区分出来（基线取 0），但它的时间单位没确认，确认前不要用。
2. **增量**。之后每次计数回调产出 `max(0, 新值 − 上次值)`，上下行分别算，然后更新上次值。新值小于上次值时产出 0 并把上次值重置为新值。累加沿用仓库里的 `saturatingAdd`。
3. **移除**。移除回调里只清状态，不再查询。1.1 实测最终计数在移除之前送达；探针里要再确认顺序固定是「最终计数 → 移除」，并统计「移除时从未收到过计数」的来源数量。
4. **manager 重建**（睡眠唤醒或回调中断后）。新 manager 里同一条连接是新的来源对象。用 `(uniqueProcessID, provider, 本地端点, 远端端点)` 作键保留旧状态，重建后首次计数与旧值做差，可以补上重建期间的字节，替代现在的 `NettopRestartGapRecovery`。旧状态超过 60 秒没被认领就丢弃，沿用现有的 60 秒上限；单连接单次增量沿用 10 Gbps × 间隔的上限。应用重启跨不过去，这部分与现状相同。
5. **查询节奏**。计数只在主动查询和连接关闭时到达。采集队列上的定时器每 5 秒查询一次，`leeway` 1 秒，以查询的完成回调作为一批的边界，把这一批增量一次交给主线程。不需要 1 秒采样，短连接由关闭时的最终计数覆盖。界面可见时是否加密到 1–2 秒属于实时速率功能，不在这一步做。
6. **时间**。样本时间用收到回调时的 `Date()`。现有 `ingest` 走的是 nettop 的时钟字符串（`Self.sampleDate(for: delta.sampledAt)`，`ByteTraceViewModel.swift:1528` 起），NStat 路径要直接传 `Date`，不要为了复用而伪造时钟字符串。

### 6.3 逐连接分类（替代按通道推断）

分类用最近一次计数字典里的接口信息，不用新增时的：连接建立前接口索引可能是 0。接口索引用 `if_indextoname` 转成名称后缓存，网络路径变化时清缓存。按顺序判断，命中即停：

1. 回环接口，且本地端点属于当前系统代理端点：这是代理监听端。按 pid 走现有的 `registerDetectedProxy` 登记，然后丢弃。对应现在的 `TrafficFilter.proxyListenerProcessTokens`（`TrafficFilter.swift:48`）。
2. 回环接口，且远端端点属于当前系统代理端点：应用侧经系统代理流量，记 `proxied`，再用本地端点查 mihomo 连接表细分。对应 `shouldKeepLoopback`。
3. 其他回环连接：丢弃（本地 IPC）。
4. 接口名以 `utun` 开头：要求本地、远端都有端口且远端不是回环（`shouldKeepTunnel` 的条件），记 `proxied` 并查 mihomo；归属后如果是代理进程，丢弃（utun 镜像，对应 `shouldKeepAfterAttribution`）。
5. 其他有名称的接口：非代理进程记 `direct`；代理进程照现状记到 `proxy:` appKey，不记路径（现有 `ingest` 已处理）。
6. 接口索引为 0 或取不到名称：**需用户决定**。现在的外部通道用 `-t external`，这类来源不计入。候选做法是按计数里的 `rxWiFiBytes + rxWiredBytes`（及 tx 对应项）记 `direct`。先在探针里统计这类来源的字节占比，把数字报给用户，再定。

第 1 条与第 2 条是同一条流量的两个套接字，两条都要处理；只做第 2 条会漏掉代理自动识别，只按接口记会把代理监听端记成应用流量。

归属要在来源新增时解析并按 `uniqueProcessID` 缓存（1.3 第 7 项）。`SystemProcessIdentityResolver` 不在主线程时会 `DispatchQueue.main.sync`，所以第一版保持现状：采集队列只做计数与分类，归属和聚合仍经 `Task { @MainActor }` 回主线程。把归属挪到采集队列是 §3 提到的另一件事，不要在同一次改动里做。

### 6.4 数据源选择与回退（对应 1.5 第 4 步）

写入是累加的，重复写入无法撤回，所以规则从严：

1. 数据源在 `start()` 里选定，一次进程生命周期内只允许从 NStat 降到 nettop，不允许反向切换，不允许两者同时向聚合器写入。
2. 启动探测全部通过才用 NStat：`dlopen` 成功；用到的每个函数和字典键 `dlsym` 都非空；manager 创建成功；首次全量查询在 3 秒内完成且至少有 1 个来源。任何一项失败都走现有双通道，并写一条 `collector_events`。读取 `sysctl net.statistics_privcheck` 记入这条事件，值为 1 时直接走 nettop。
3. 运行中连续 3 次查询没有完成回调，判定 NStat 失效：先销毁 manager，再 `flushNow()`，然后启动 nettop 双通道。nettop 两个通道各自丢弃首帧，不会与 NStat 已记的字节重叠。切换时对 `externalGapRecovery` 调 `reset()`，否则它会用上一轮 nettop 的旧基线补记这段时间。
4. NStat 采集器与 nettop 一样，只在拿到 `DataDirectoryLock` 之后启动，释放锁之前停止并清空 6.2 的全部状态。
5. 睡眠唤醒与网络切换时现有流程是「停两个采集器 → `flushNow()` → 重连」。NStat 下是否需要重建 manager 由 1.3 第 4 项的实测决定；实测前按「保留 manager，唤醒后立即查询一次」实现，并在探针里做一次合盖 10 分钟的测试。
6. 设置里的开关默认关闭，改动后下次启动生效，不做运行中切换。
7. `accounting_version` 是否升级、何时把 NStat 设为默认：**需用户决定**。

### 6.5 对账的通过标准（对应 1.5 第 2 步）

探针产出数字，按下面的标准判定；任何一项不通过就停下来报告，不进入第 3 步。

| 项 | 做法 | 通过标准 |
| --- | --- | --- |
| 字节准确度 | 沿用 `--accuracy` / `--routes` 的三个用例（直连经 TUN、经系统代理走节点、经系统代理规则直连），各下载 20 MB | NStat 计数 ÷ 实际下载字节在 1.000–1.010 |
| 与 nettop 等价 | 两者并行 10 分钟日常使用，按进程、按方向、按路径分别汇总 | 流量前 10 的进程每项差异在 ±1% 以内；超出的逐项写明原因 |
| 逐连接合计与 `-P` 一致（1.3 第 8 项） | 同上，只看外部接口 | 同上 |
| 用户态协议栈 | 用浏览器从支持 HTTP/3 的站点下载一个已知大小的文件 | 能看到 provider 3 / 5 / 8 的来源，字节与文件大小相符 |
| 启动基线 | 下载进行中启动探针 | 启动前已传输的字节不出现在增量里 |
| 关闭顺序 | 统计全部移除事件 | 「最终计数先于移除」100% 成立；否则报告比例 |
| 开销 | 同一台机器、同样负载下各跑 10 分钟空闲与 10 分钟下载，用 `ps -o time` 取进程累计 CPU 时间之差，`top -l 2 -stats pid,command,cpu,idlew` 取唤醒数 | NStat 方案（应用进程）不高于现状（应用进程 + 两个 nettop 子进程）之和 |
| 连接数压力（1.3 第 5 项） | 并发建立 2000 条以上连接 | 查询完成耗时与 CPU 记录在案，查询不超时 |
| 长时间运行（1.3 第 4 项） | 运行 24 小时以上，含一次睡眠唤醒、一次 Wi-Fi 切换 | 回调不中断，或中断后按 6.4 第 3 条降级 |

**第 1 项，回收空闲页**（读代码）：

- `ByteTraceViewModel.swift:1810` 的注释写明了一个已有决定：不按删除行数自动 VACUUM，避免周期性重写整个数据库。所以这里只做有条件的一次性回收，不做周期任务。
- `UsageStore.vacuum()`（`UsageStore.swift:965`）整个执行期间持有 `lock`。落库在主线程（5 秒定时器 → `flushNow()`），会一直等到 VACUUM 结束，界面在这段时间无响应。样本不会丢，聚合结果在内存里。
- 动手前先量耗时：用 `sqlite3 <正式库> ".backup <副本路径>"` 复制一份，在副本上执行 `VACUUM` 计时，把数字写进提交说明。
- 触发条件：`PRAGMA freelist_count × page_size` 不少于 64 MB 且占文件 30% 以上；`visibleSurfaceCount == 0`（没有界面可见）；数据目录所在卷的可用空间不少于库文件的 2 倍；每次进程生命周期最多一次。在 `retentionQueue` 上执行，复用 `retentionCleanupInProgress` 门控，排在当天的 `purgeBuckets` 之后。

- VACUUM 不能在事务内执行，执行时不能有未 finalize 的语句。失败只记 `collector_events`，不提示用户，不重试到下次启动之前。
- 验收：在正式库副本上跑一遍，文件大小、各表行数、`daily_usage` 字节合计前后一致；`UsageStoreConcurrencyTests` 里加一个「VACUUM 期间并发 apply 不丢样本」的用例。

**第 3 项，`WITHOUT ROWID`**：`deleteBuckets` 用了 `rowid IN (SELECT rowid …)`，`WITHOUT ROWID` 表没有 rowid，这条语句必须同时改写。先完成 §3 的后台迁移与进度显示，并在正式库副本上跑通、量出耗时与体积收益，再决定做不做：**需用户决定**。

### 7.1 代码已确认的问题

#### 7.1.1 mihomo 路径缓存读取时不检查过期

**依据（读代码）**：[MihomoConnections.swift](../Sources/ByteTraceCore/Mihomo/MihomoConnections.swift#L110) 的 `update(with:at:)` 在成功收到新快照时删除超过 120 秒的条目，但 `route(forLocalEndpoint:)` 直接返回条目、不检查时间。`isActive` 有时间判断，正式路径判断未使用它。[ByteTraceViewModel.swift](../Sources/ByteTraceApp/ByteTraceViewModel.swift#L1398) 的 `supplementalRoute` 直接查缓存；`finishMihomoFetch` 失败时清掉控制器地址，没有清掉路径缓存（1477 起）。

**影响**：采集仍在运行、控制器请求持续失败且没有新快照时，旧条目可超过约定的 120 秒继续被使用。缓存仅以本地 IP 和端口为键，复用端点的新连接可能沿用旧出口。代码行为已确认；正式环境发生频率与影响字节数未测。此问题影响路径分类，总字节数不由这个缓存决定。

**建议**：先保证读取时也校验条目有效期，失效时返回未知。控制器重启或切换时隔离旧缓存和旧请求的晚到结果；现有异步请求在回到主线程前就更新 tracker，单独调用一次 `removeAll()` 不能完整解决晚到响应问题。协议、连接 ID、远端端点与时间能否共同用于匹配，需要核对双方实际提供的字段，不能假定本地端点唯一。

**验收（待运行）**：不再调用 `update`，只推进时钟超过有效期，查询必须失效；有效期内的已关闭连接仍能支持延迟到达的 nettop 帧；控制器切换后的旧响应不能重新填入缓存；端点冲突不能静默确定出口；分类变化前后总字节不变。TTL 边界用可注入时钟验证，不靠测试实际等待 120 秒。

#### 7.1.2 准确性与路径探针失败未传递到退出码

**依据（读代码）**：[ByteTraceProbe/main.swift](../Sources/ByteTraceProbe/main.swift#L592) 的 `accuracyPassed`、`routesPassed` 用于打印分项结果，没有进入最终成功条件。函数末尾只检查两个通道是否有帧、schema 是否兼容及存储错误数，之后打印最终 PASS 并返回 `0`（647–665）。`--restart-check` 单独返回失败码，不属于这个问题。

**影响**：`--accuracy` 或 `--routes` 可以打印 FAIL，同时最终仍返回成功。使用退出码验收的脚本无法可靠识别失败。在完成修复前，不能只凭命令返回 `0` 或最后一行 PASS 判断 §6.5 通过。

**建议**：把本次请求的各项验收结果汇总到唯一最终结果，并决定退出码；没有执行的必需用例不能作为通过。无系统代理等情况应明确记为跳过，不能据此宣布完整代理矩阵通过。

**验收（待运行）**：字节不达标、路径不达标、下载失败、无有效用例分别导致相应验收失败和非零退出码；所有必需用例通过时才返回成功；普通 `--duration` 模式保持原有语义。结果汇总的失败分支可用固定输入验证，不必每次产生真实网络流量。

**对 §6.5 的补充**：当前 `reportAccuracy`（342 起）判定的是下载比例 `0.97–1.10`，上传仅打印；`reportRoutes`（359 起）要求期望路径的下载占比至少 90%。这些现有判定不等于 §6.5 为 NStat 提出的 `1.000–1.010` 标准。新探针应明确各自使用的阈值、字节口径及上下行结果，不能直接把旧探针 PASS 当成新标准通过。增加上传、短连接、混合本地 IPC、进程快速退出的受控用例；两种采集器之间一致也不能替代与受控传输结果的对照。

### 7.2 需要决定的统计取舍

#### 7.2.1 未确认出口的流量按比例分摊

**现状（读代码）**：[ByteTraceViewModel.swift](../Sources/ByteTraceApp/ByteTraceViewModel.swift#L250) 的 `RouteSplit` 将 `.proxied` 按该应用已确认的「节点 : 规则直连」比例分摊；该应用没有已确认出口时，使用同一范围内全部应用的比例。两者均不可用时才保留为 `unknownBytes`。`coverage` 表示有路径行的流量占比，包含出口未知及分摊部分，不能解释为出口已确认比例。

按实现可推导的反例：应用 B 有 100 MB `.proxied`，自身没有节点或规则直连记录；其他应用的已知出口全部走节点时，B 显示 100 MB 代理流量。其他应用后续增加规则直连流量，B 的显示值也会改变，即使 B 没有新增流量。这是静态推导，尚未做界面复现。

**影响边界**：上述比例分摊发生在展示计算中，不能描述成 SQLite 已把 `.proxied` 全部改写为 `.proxyNode`。[RouteBreakdownView.swift](../Sources/ByteTraceApp/RouteBreakdownView.swift#L85) 已在悬停说明中提示「按同一应用」估算，但未说明跨应用参照。捕获到的连接与轮询之间已经结束的连接，其出口分布也未证明相同。

**候选处理，需用户决定**：保留已识别的直连、节点、出口未知分别展示；或继续提供估算，同时明确展示估算量、参照范围和已确认比例。建议优先取消跨应用分摊；是否取消同应用分摊单独决定。界面、导出说明和比例分母应一致，不把估算写回已确认路径。

**验收（待运行）**：覆盖全部未知、只有少量已知、跨应用参照变化、没有历史路径行等输入；按照所选方案明确哪些显示值允许随参照变化；总字节保持不变，路径缺失与出口未知仍可区分。

#### 7.2.2 同名短命进程沿用完整宿主归属

**现状（读代码）**：[ProcessAttributor.swift](../Sources/ByteTraceCore/Attribution/ProcessAttributor.swift#L548) 对无法解析身份的进程，以 `nettopProcessName` 查询 `lastResolvedByName`，复制上次的宿主、程序和路径等信息。这个名称回填规则独立于 `(pid, processStartTime)` 缓存，不能把本项描述成已有 PID 复用保护失效。

按实现可推导的反例：先解析到终端启动的 `curl`，再收到编辑器启动、但解析前已退出的另一个 `curl`，后者可沿用终端的宿主。`node`、`python` 等通用进程名同样无法唯一确定宿主，解释器名称还可能对应不同程序。现有测试验证了 Discord Helper 的同名回填，不能代表通用命令跨宿主的情况。

**取舍**：当前规则减少无法识别记录和条目拆分，但可能影响宿主或程序排行；正式环境的误归属比例未测。仅缩短名称缓存有效期无法消除同一时段的名称冲突。

**候选处理，需用户决定**：保留同一进程实例已有的身份快照；仅有名称证据时记录为推断，或对不能唯一确定来源的记录使用虚拟宿主，避免直接确定宿主。程序身份与宿主身份分别判断，不能因能认出工具名就认定启动者。连接新增时提前缓存身份，是 NStat 方向值得测量的收益之一。

**验收（待运行）**：同名不同宿主、同解释器不同脚本、进程退出、名称截断冲突和名称缓存启动预填；确认总字节不变且展示能解释不确定归属。历史数据缺少原始证据时不能按新规则猜测重分配；若改变持久化身份键，仍须按项目约定设计迁移。

### 7.3 停止与退出的完成确认

**现状（读代码）**：`NettopCollector.emitParserEvent`（249 起）先经 `DispatchQueue.main.async` 投递，[ByteTraceViewModel.receive](../Sources/ByteTraceApp/ByteTraceViewModel.swift#L1126) 再创建 `Task { @MainActor }` 处理。`flushAfterStop`（1753 起）另外排入主队列，`shutdown`（720 起）运行 50 毫秒 RunLoop 后落库。`stop` 在调用异步落库安排后释放数据目录锁（627 起）。

**证据边界**：代码中没有明确的「所有已接收尾帧处理完成」确认。主队列 block 排队顺序不足以证明其另行创建的 Task 已完成；固定等待时长也没有表达这个完成条件。本轮未复现尾帧丢失，不把它列为已实测丢数据。此项与 ROADMAP §3.2 已记录的问题一致。

**建议**：停止接收新数据，排空当前运行代次已接收的帧，等待最后事务完成，再释放锁或允许正常退出。采集批次携带通道、运行代次和序号；旧代次的合法尾帧需要排空，不能一律丢弃。§6.4 的 NStat 降级也应遵守这一顺序。涉及协调方式的实现单独规划，不与数据源替换混成一次改动。

**验收（待运行）**：人为延迟尾帧处理、两个通道交错退出、停止后立即重新开始、另一个实例接管、末次落库失败；确认每批只写一次、正常停止后无未处理尾帧、写入失败不会被报告为保存成功。

### 7.4 NStat 方案的证据限定与候选改进

**权限限定（公开源码）**：Apple 的 [XNU `nstat_client_handle_add_all`](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/net/ntstat.c#L6443) 对 `NSTAT_PROVIDER_UDP_SUBFLOW`、`NSTAT_PROVIDER_CONN_USERLAND` 即使在 `nstat_privcheck == 0` 时也检查权限。因此 §1.1 的权限结论应限定到实际验证的来源，不能扩展成全部 provider 均免权限。公开源码分支不等于本机内核实现；此条件也不能证明 §6.1 的 TCP／UDP／QUIC 订阅不可用或必然漏采。

§6.1 已区分订阅层面与运行时是否收到有效字节，继续按 §6.5 验证。只有来源数量或首次查询成功，仍不能证明覆盖完整。记录 provider、实际上下行字节和受控用例的对应关系；不要为了满足条件去请求产品不需要的额外权限。

**候选：独立辅助进程承载私有接口，未验证收益、尚未选定。** 进程内 `dlopen` 与符号检查能处理部分不可用情况，但私有接口调用若直接使主进程崩溃，主进程内的回退代码无法继续执行。独立辅助进程可隔离这类崩溃，并由主应用恢复到 nettop；代价是增加进程通信、打包和生命周期管理。它与当前进程内方案应作为备选比较，不能先宣称更省电或强制替换 §6 的实现路径。测量开销时需计入辅助进程。

**候选：分别记录三类证据。** 字节来自正常计数还是残差补记、宿主来自已解析身份还是名称回填、出口来自连接匹配还是比例估算，分别记录。当前 `SupplementalResidualTracker` 会按历史中的主导类别给残差分配路径，因此不能把所有存量 `.proxyNode` 行直接标成逐连接确认。可先增加仅用于探针的证据统计，测出推断占比，再决定是否新增持久化字段；不为此默认保存原始地址或完整连接日志。

**候选：通道健康状态。** 按最后成功帧和运行代次识别采集停滞，区分正常零流量、未采集和分钟明细已清理。健康时间覆盖率与已确认出口比例分开表达，都不能称为流量准确率。后续周期对比应结合这些状态，避免把漏采解释为用量下降；具体界面和存储设计另行决定。

### 8.2 NStat 的 Swift 绑定（已实测可用）

```swift
typealias NStatRef = UnsafeMutableRawPointer
typealias NStatNewSourceBlock = @convention(block) (NStatRef?, UnsafeMutableRawPointer?) -> Void
typealias NStatDictionaryBlock = @convention(block) (CFDictionary?) -> Void
typealias NStatVoidBlock = @convention(block) () -> Void

let handle = dlopen("/System/Library/PrivateFrameworks/NetworkStatistics.framework/NetworkStatistics", RTLD_NOW)

// 函数：dlsym 得到的地址按 @convention(c) 函数类型转换
let create = unsafeBitCast(dlsym(handle, "NStatManagerCreate"),
    to: (@convention(c) (CFAllocator?, DispatchQueue, NStatNewSourceBlock) -> NStatRef?).self)
// 同样写法的其余函数及其类型：
//   NStatManagerDestroy                       (NStatRef) -> Void
//   NStatManagerAddAllTCP / AddAllUDP         (NStatRef) -> Void
//   NStatManagerQueryAllSourcesUpdate         (NStatRef, NStatVoidBlock?) -> Void
//   NStatSourceSetDescriptionBlock            (NStatRef, NStatDictionaryBlock?) -> Void
//   NStatSourceSetCountsBlock                 (NStatRef, NStatDictionaryBlock?) -> Void
//   NStatSourceSetRemovedBlock                (NStatRef, NStatVoidBlock?) -> Void

// 字典键：dlsym 得到的是「存放 CFStringRef 的变量」的地址，要再取一次值
let rxKey = dlsym(handle, "kNStatSrcKeyRxBytes")!
    .assumingMemoryBound(to: Unmanaged<CFString>.self).pointee.takeUnretainedValue() as NSString
```

用到的键与值类型（实测）：`kNStatSrcKeyPID`（`processID`，数字）、`kNStatSrcKeyUPID`（`uniqueProcessID`，数字）、`kNStatSrcKeyProcessName`（字符串）、`kNStatSrcKeyRxBytes` / `TxBytes`（数字）、`kNStatSrcKeyInterface`（接口索引，数字）、`kNStatSrcKeyInterfaceTypeLoopback`（`ifLoopback`，布尔，只在为真时出现）、`kNStatSrcKeyProvider`（字符串 `TCP` / `UDP`）、`kNStatSrcKeyLocal` / `kNStatSrcKeyRemote`（`Data`，内容是 `sockaddr_in` 或 `sockaddr_in6`，第 2 个字节是地址族，端口为网络字节序）。分接口的字节键没有单独验证导出符号以外的用法，名称是 `kNStatSrcKeyRxWiFiBytes`、`RxWiredBytes`、`TxWiFiBytes`、`TxWiredBytes`。

调用顺序与约束：

1. `NStatManagerCreate(nil, queue, block)`，`queue` 是自己的串行队列。新来源回调、描述、计数、移除、查询完成回调都在这个队列上执行，所有状态只在这个队列上读写。
2. 在这个队列上依次调用 `AddAllTCP`、`AddAllUDP`，然后立即调用一次 `QueryAllSourcesUpdate` 作为启动基线（§6.2 第 1 条）。
3. 新来源回调里只做三件事：分配一个自增的整数 ID，建立状态，给来源设置描述、计数、移除三个 block。block 捕获这个整数 ID，不捕获来源指针。不要读新来源回调的第二个参数。
4. 移除回调里删除该 ID 的状态。之后不再使用这个来源指针。
5. 之后只用 `QueryAllSourcesUpdate` 查询，以它的完成回调作为一批的边界。
6. 停止时在队列上调用 `NStatManagerDestroy`，并置一个「已停止」标记；销毁之后是否还会有回调没有测，所有回调入口先检查这个标记。
7. 任何一个 `dlsym` 返回空都视为不可用（§6.4 第 2 条），不要对空指针做 `unsafeBitCast` 后调用。

实测脚本用 `-swift-version 5` 编译，状态是全局变量。仓库是 Swift 6 语言模式，正式代码要写成 `final class … @unchecked Sendable`，状态限定在上面的串行队列内，与 `NettopCollector` 的做法一致。脚本没有额外持有来源对象，运行 21 秒、百余次移除没有出现问题；更长时间未测。

**参数。** 都要带 `--nstat`，不带时探针行为与现在完全相同。

| 命令 | 作用 |
| --- | --- |
| `--nstat --duration N` | 只跑 NStat，每 5 秒查询一次，结束时打印汇总 |
| `--nstat --accuracy [URL]` | 只跑 NStat，用现有的三个 curl 用例对照字节与路径（始终轮询 mihomo，相当于现有的 `--accuracy --routes`） |

**汇总输出（三种模式结束时都打印）。** 每行一个 `[nstat] 键=值`：新增来源数、移除数、移除时从未收到计数的数量、最终计数先于移除的数量、移除后仍收到回调的数量、按 provider 的来源数与字节、按 §6.3 六类的来源数与上下行字节、接口未知一类占全部增量字节的比例、最长进程名及字节数、查询次数与耗时的最小／中位／最大值、未在 3 秒内完成的查询次数、`getrusage(RUSAGE_SELF)` 与 `RUSAGE_CHILDREN` 的用户态与内核态毫秒数。nettop 模式结束时也打印同样两行 CPU，供开销对比。

**`--nstat --accuracy` 的判定。**

- 用例与现有 `runProbe` 相同：`direct`、`system_proxy`、`rule_direct`，沿用 `runCurl`。启动后先等启动基线查询完成，再开始下载；每个 curl 退出后等 2 秒，再查询一次。
- 计入的字节：pid 等于该 curl 的全部来源中，属于「经系统代理」「TUN」「外部接口」三类的增量之和。「接口未知」一类的字节单独打印，不计入。
- 下载比值 = 计入的下行 ÷ curl 的 `size_download + size_header`（现有 `CurlResult.downloadBytes` 已是这个和），通过区间 1.000–1.010（§6.5）。上传只要求计入的上行不小于 curl 的 `size_upload + size_request`，并打印比值。
- 路径：`system_proxy` 期望 `proxy_node`、`rule_direct` 期望 `proxy_rule_direct`，期望路径的下行占比不低于 90%（沿用现有标准）。
- 退出码按 8.5 的规则。

**`--nstat --compare` 的对账算法。**

1. 同时启动 nettop 两个通道和 NStat。nettop 一侧完全沿用现有 `handleCollectorEvent` 的处理（过滤、残差、归属后丢弃代理的 utun 镜像）。
2. 节拍对齐：NStat 不用自己的定时器，每收到一帧外部通道的 `frameCompleted` 就触发一次 `QueryAllSourcesUpdate`，这样两边的批次边界相差只有查询耗时。
3. 统计窗口：从「NStat 启动基线已完成之后的第一帧非基线外部帧」开始，到停止前最后一帧外部帧触发的查询完成为止。窗口外的增量两边都不计。补充通道是 1 秒一帧，窗口两端各有最多 1 秒的错位，属于已知误差。
4. 匹配键是 pid（nettop 一侧用 `NettopProcessToken(rawValue:).pid`）。不用进程名，nettop 的名称会截断。
5. 每个 pid 比较两组数，上下行分开：
   - 外部：nettop 外部通道的字节，对比 NStat「外部接口」类的字节。代理进程也参与这一组。这一组同时回答 §1.3 第 8 项。
   - 补充：nettop 补充通道最终接受的字节（含残差），对比 NStat「经系统代理」与「TUN」两类之和。归属为代理传输的进程，其 TUN 类字节两边都不计。
   - NStat「接口未知」类单独一列，不并入任何一组。
6. 路径：对补充一组再按 `proxied` / `proxy_node` / `proxy_rule_direct` 分别打印两边的下行字节，只打印不判定。
7. 判定：按两边合计字节取前 10 个 pid，每个 pid 的四个数（两组 × 上下行）各自满足「相对差不超过 1%，或绝对差不超过 64 KB」为通过。64 KB 这个下限是本节新加的，用于避免小流量进程因个别数据包被判不通过；用户可以改。
8. 输出：每个数一行 `[compare] pid=… name=… group=external|supplemental dir=down|up nettop=… nstat=… diff=…% OK|MISMATCH`，最后一行 `[compare] result=PASS|FAIL`。不通过的行不要删也不要解释成通过，原样报告。

归属：NStat 一侧在来源首次拿到 pid 时解析身份并缓存（§1.3 第 7 项）。`SystemProcessIdentityResolver` 不在主线程时会同步等主线程，所以和应用一样，把来源事件切回主线程再解析，不要在 NStat 队列里直接调用。

**启动基线用例（§6.5）。** 不单独加参数：先在另一个终端开始限速下载，再运行 `--nstat --duration 20`，核对该 curl 的 pid 在汇总里的下行约等于「速率 × 探针运行时长」，而不是下载开始以来的总量。

### 8.5 探针退出码（对应 §7.1.2）

只改 `Sources/ByteTraceProbe/main.swift`。

- 每个用例的结果分三种：通过、失败、跳过。curl 启动失败、输出无法解析、curl 退出状态非 0、字节或路径不达标都是失败。当前没有系统代理时，`system_proxy` 与 `rule_direct` 是跳过。
- 退出码：`0` 表示本次请求的检查全部通过且没有跳过；`1` 表示有任何失败，或原有的三项检查（两个通道都有帧、格式兼容、无存储错误）不满足；`2` 表示没有失败但有用例被跳过。`2` 这个取值是本节新定的，用户可以改。
- 最后一行 `[result]` 与退出码一致：`PASS`、`FAIL`、`PARTIAL`，并列出失败或跳过的用例名。有失败时不再打印现在的 `PASS: nettop CSV → …`。
- 不带 `--accuracy` / `--routes` 的普通模式，输出与退出码保持原样。`--restart-check` 不动。
- 现有阈值不改：下载比值 0.97–1.10，期望路径占比不低于 90%。它们是 nettop 探针的标准，与 8.3 的 NStat 标准分开。
- 把「各用例结果 → 退出码与最终行」写成一个不依赖网络的纯函数，放在 `main.swift` 里。探针 target 没有测试，验证方式是运行一次必然失败的用例：`swift run ByteTraceProbe --accuracy http://127.0.0.1:1/`，然后 `echo $?`，应为 `1`（curl 连接被拒绝，不产生外部流量；探针本身要等约 20 秒）。

### 8.6 mihomo 路径缓存（对应 §7.1.1）

涉及 `Sources/ByteTraceCore/Mihomo/MihomoConnections.swift`、`Sources/ByteTraceApp/ByteTraceViewModel.swift` 的 mihomo 一段（1404–1496 行）和 `Tests/ByteTraceCoreTests/MihomoTests.swift`。

1. **读取时校验有效期。** `route(forLocalEndpoint:)` 增加带默认值的参数 `at now: Date = Date()`，条目的 `lastSeen` 距 `now` 超过 `retention` 时返回 `nil`。现有两个调用点（`ByteTraceViewModel.swift:1401`、探针 `main.swift:422`）不用改。
2. **晚到的结果不写入缓存。** 现在 `tracker.update` 在后台任务里执行（1466 行），早于回到主线程的检查。改为后台任务只做请求与解析，把快照带回主线程；`finishMihomoFetch` 里先判断 `mihomoController == controller`、`readsMihomoConnections`、`wantsCollection` 都成立，再调用 `update`，否则丢弃这次结果。关闭开关或停止采集时 `updateMihomoPolling` 已经把 `mihomoController` 置空并清缓存，晚到的结果因此对不上控制器。
3. **换控制器时清缓存。** `mihomoTimerFired` 里重新发现到的控制器与上一个成功用过的不同时，调用 `removeAll()`。请求失败时不清：有效期内的条目还要用来匹配晚到的 nettop 帧，过期由第 1 条处理。
4. **端点冲突。** 同一份快照里同一个本地端点出现两次且出口不同（例如同端口的 TCP 与 UDP）时，这个端点记为 `.proxied`（出口未知），不取其中任何一个。出口相同时照常记录。不为此新增协议字段。
5. **测试**（都用注入的 `at`，不实际等待）：超过有效期后查询返回 `nil`；有效期内、快照里已经没有的连接仍能查到；冲突端点返回 `.proxied`；`removeAll()` 之后查不到。第 2、3 条在应用 target，没有测试，靠阅读代码确认，并在提交说明里写明未经运行验证。

分类变化不影响总字节：路径只写 `daily_route_usage`，查不到时记 `proxied`。
